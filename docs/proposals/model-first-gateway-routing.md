# 按模型选择的统一网关接入方案

状态：用户已确认并授权实施。本方案调整模型选择和路由归属，不代表文中能力已经交付。

## 1. 使用方式和目标

打开 Agent 后，用户选择“网关”或“官方登录”。选择网关时，只选择模型，日常操作中不再选择 Provider、API 地址、Key 或上游协议。

在设置中维护模型目录。每个模型别名对应一个 Provider，以及该模型实际支持的协议和各协议上游模型名。默认按 Agent 原生协议自动匹配，也可在设置中固定上游协议。Agent 只向稳定的网关入口发送模型别名，网关完成路由。

例如，在设置中建立以下目录：

| 模型别名 | 显示名称 | Provider | 上游模型名 | 协议策略 |
| --- | --- | --- | --- | --- |
| `deepseek-fast` | DeepSeek Flash | OpenCode Go | `deepseek-v4.1-flash` | 自动匹配，限该模型已配置并验证的协议 |
| `coding-main` | 主力代码模型 | 内网服务 | `code-model-v1` | 自动匹配，示例仅支持 Responses |
| `reasoner` | 推理模型 | Provider A | `reasoner-v1` | 固定 Chat Completions |

`code-model-v1` 和 `reasoner-v1` 是配置示例。真实可用模型以相应服务为准。

用户在 Claude Code 或 Codex 中选择 `deepseek-fast`，不需要了解它由 OpenCode Go 提供，也不需要在两个 Agent 中重复配置服务地址。把该别名改到另一个 Provider 后，模型入口保持稳定；已运行会话如何接收变更，见第 7 节。

目标是统一选择方式和配置来源。Agent 的原生协议、上游支持的能力、历史会话兼容性仍由实现检查，界面不能用“网关”标签掩盖这些限制。

## 2. 与现有实现的差别

现有 `ModelSourceSelect` 先列出 Provider，再列出该 Provider 的模型。`gateway:<providerId>` 仍把物理 Provider 放进了用户的会话选择，`GatewayRoute` 也主要绑定供应商账号。

本方案把选择改为：

```text
Agent
  接入方式：网关 / 官方登录
  网关模型：DeepSeek Flash / 主力代码模型 / 推理模型

设置 → 模型与网关
  模型：别名 → Provider + 上游模型映射 + 协议策略（默认自动匹配）
  Provider：地址、可用协议、凭据
  Agent 默认：接入方式、默认模型或官方账号
```

模式和模型的选择保存在会话中。Provider 绑定只在模型设置和网关运行状态中出现，不再作为普通会话表单的选择项。

## 3. 范围和交付边界

本次包含统一模型目录、二选一的接入方式、按请求模型解析路由、协议适配、原生模型菜单接入、配置迁移和兼容切换规则。保留现有终端/TUI、ACP、MCP、Skills、hooks 和加密凭据服务。

首批验收覆盖已有自定义 API 启动路径的 Claude Code、Codex、OpenCode、Pi、Oh My Pi。其他 Agent 使用相同交互契约，但必须先完成其插件的自定义 API 接入。不能因为它能运行终端或支持 ACP，就宣称它能接网关。

对于没有自定义 API 接入能力的 Agent，“网关”显示不可用及具体原因。对于没有官方账号登录方式的 Agent，不显示一个实际会走第三方 API 的“官方登录”。原有自有配置会话通过兼容路径保留，见第 10 节。

本次首先面向本机 Agent。远程 SSH Agent 需要远端网关或受控的私有连接能力，不能把桌面的 `127.0.0.1` 地址直接注入远程进程。远程接入未完成时，应显示限制，不把选择网关的请求改成直连。

账号池、自动故障转移、负载均衡、文件/音频/批处理接口、WebSocket、记忆和费用估算不包含在本次交付中。用量账本后端的选择单独处理，不把接入 Keeper 作为模型路由改造的前置条件。

## 4. 日常交互

### 4.1 新建会话

1. 选择 Agent，沿用该 Agent 的接入默认值。
2. 选择“网关”或“官方登录”。“恢复 Agent 默认”是重置操作，不增加第三种接入模式。
3. 网关模式显示统一模型列表，可按显示名称和别名搜索。条目不要求选择 Provider。
4. 官方登录模式使用该 Agent 自己的账号和模型目录，网关模型列表不参与。
5. 启动前检查模型、凭据引用、协议适配和模型能力。检查失败时保留用户的选择并指出应修复的设置。

网关未启动、选中模型被停用或某个 Provider 缺少 Key，都不自动切到官方登录，也不改用另一个 Provider。

### 4.2 已打开会话

主界面显示“网关 · DeepSeek Flash”或对应的官方账号。Provider、上游模型和协议放在只读路由详情中，供排障使用。

切换网关模型继续使用模型选择器。实现判断能否原位更新、应等待当前轮结束、需要重启 Agent，或需要新建会话，并提前显示结果。普通表单不重新要求用户选择 Provider。

切换“网关 / 官方登录”需要重新建立 Agent 的启动配置和认证环境。可以恢复历史时沿用已验证的恢复路径；受服务端状态约束而不能恢复时，明确提示新建会话。启动校验和替代会话准备成功前，不删除原会话记录。

### 4.3 Agent 自己的模型菜单

TUI 的 `/model`、OpenCode/Pi 等原生模型列表，以及 ACP 的模型选择，读取或投影同一模型目录。Claude Code 2.1.242 及以后通过会话级 `modelPicker` 设置发布任意别名，不依赖会过滤部分别名的自动发现。Agent 配置中的 Provider 名称保持稳定，例如 `emdash-gateway` 或 Codex 的 `custom-gateway`，其后列出多个公共模型别名。

原生 CLI 的配置格式可能仍包含一个内部 Provider 标识，但用户不需要按上游 Provider 重复选择。不能控制的 CLI 原生菜单只能按其公开配置能力接入，不伪造菜单行为。

部分客户端在进程启动时加载模型目录。新增模型、修改上下文窗口或工具能力时，如果该适配器不能安全刷新，就显示“重启后可用”。已经加载的模型间切换优先使用客户端支持的方式。

Claude Code 的 `opus`、`sonnet`、`haiku`、`fable` 等角色别名默认指向启动时选中的网关模型，避免后台请求使用未配置的官方模型名。首批统一使用所选模型，独立的辅助模型角色表单作为后续扩展。不能承诺原生 `/model` 命令会同步改写进程环境中的全部角色绑定。

## 5. 设置和数据归属

### 5.1 模型设置

模型编辑表单包含：

| 字段 | 规则 |
| --- | --- |
| 显示名称 | 供界面展示，可修改，不影响 API 请求标识 |
| 模型别名 | Agent 请求中的公共 `model`，在网关目录中唯一 |
| Provider | 引用已保存的供应商或已支持的网关上游账号 |
| 上游模型名 | 实际发送给 Provider 的模型标识，可手动填写或从手动发现结果选择；不同协议可分别覆盖 |
| 可用协议 | 从 Provider 已启用的协议中选择该模型确实支持的协议；Provider 支持不代表该模型在该协议下可用 |
| 协议策略 | 默认自动匹配 Agent 原生协议；高级设置可固定某个上游协议 |
| 转换目标 | 原生协议不可用时，从模型已配置协议中选择 SDK 支持且已验收的转换目标，也可显式覆盖；不存在可用方向则报不兼容 |
| 模型能力 | 上下文窗口、输出上限、工具、图片、推理和搜索等已知能力；未知值保持未知 |
| 启用状态 | 停用后阻止新的模型选择；已运行会话按显式的停用规则处理 |

别名建议采用适合 CLI 参数和目录的稳定标识，例如 `deepseek-fast`。使用期间可以改显示名称；被会话引用的别名不直接改名或复用给其他模型，应通过新建别名和迁移选择处理。

同一上游模型可以发布多个别名，但每个别名只绑定一个 Provider。该 Provider 的不同协议属于同一逻辑路由的确定性变体；每个请求只能解析出一条具体路由。首版不按 Agent、负载或错误随机选择不同 Provider。不同协议的模型名若不相同，需显式声明它们属于同一发布模型，不能靠名称猜测等价。

### 5.2 Provider 设置

Provider 保存名称、公共地址、各协议地址、默认 Key、独立协议 Key 和已有账号引用。它不再维护另一份可独立编辑的“对 Agent 发布的模型列表”。发现到的上游模型是选择和校验的来源，发布目录由模型设置统一维护。

保留已有 HTTP/HTTPS 地址策略、协议独立 Key 和加密存储。模型目录只存凭据引用，不含明文密钥。原生官方账号仍由官方登录入口管理；不把某个 Agent 的官方订阅默认开放给其他 Agent 使用。已存在的 SDK 网关 OAuth 账号只保留其已定义的支持范围。

配置校验和在线验证分开：有 Key 不等于 Key 有效，能列模型也不等于工具调用可用。提供手动“测试路由”，不新增后台反复探测供应商的任务。

### 5.3 建议契约

以下类型表达领域关系，不要求新增同名数据库表。会话继续沿用现有字段：网关保存 `modelSource = gateway:models` 与公共别名 `sourceModel`，默认官方配置保存 `null`，独立官方账号保存其账号引用。运行路由快照由网关所属的持久存储维护。

```ts
type ModelAccess =
  | { mode: 'gateway'; modelId: string }
  | { mode: 'native'; accountId?: string };

type GatewayModel = {
  id: string;
  alias: string;
  name: string;
  enabled: boolean;
  revision: number;
  providerId: string;
  protocolModels: Partial<Record<ProviderProtocol, { upstreamModel: string }>>;
  protocolPolicy:
    | {
        mode: 'auto';
        conversionTargets?: Partial<Record<ProviderProtocol, ProviderProtocol>>;
      }
    | { mode: 'fixed'; protocol: ProviderProtocol };
  contextWindow?: number;
  nonReasoning?: boolean;
  webSearch?: boolean;
  codexReasoning?: CodexReasoning;
};
```

`id` 是内部稳定身份；`alias` 是公开请求名；`protocolModels` 是各协议下的物理模型名。三者分开，避免改显示名称或 Provider 时误改历史引用。表单可以用一个默认上游模型名批量填写协议映射，再对个别协议覆盖。

`conversionTargets` 可覆盖自动转换目标；不配置时先选同协议，缺少同协议再按固定的已支持方向顺序选择。固定协议模式同样受转换注册和能力校验约束。

推荐在现有 app settings 领域增加有版本的模型路由配置。Provider 连接和凭据仍归 `model-providers`；模型目录、路由修订和会话绑定归 `model-gateway`；会话接入选择归 `conversations`；Agent 的启动参数归相应启动适配层。对既有版本化 JSON 的改动使用所属 schema 的版本机制，不手写 SQL 迁移。

Browser 通过 owning slice 的 typed Wire client 读取模型目录和编辑设置。准备真实启动环境、读取上游 Key 和签发会话能力令牌都留在 Node 侧。沿用现有设置写入串行和发布机制；新配置保存失败时，已发布的有效配置保持不变。

## 6. 按模型解析请求

```mermaid
flowchart LR
  A[Agent 选择网关和模型] --> G[稳定网关入口]
  G --> M[按请求 model 查模型目录]
  M --> S[按入站协议选择上游协议]
  S --> R[固定本次路由快照]
  R --> P{协议是否相同}
  P -->|相同| T[透传并按配置替换模型名]
  P -->|不同| C[经过验收的 SDK 协议适配]
  T --> U[指定 Provider]
  C --> U
  U --> B[响应返回与独立用量归因]
```

请求处理顺序：

1. 校验会话能力令牌、会话存在性和运行 Host。
2. 读取请求中的 `model`，在该会话可用目录中解析公共别名。
3. 从请求入口识别入站协议，按模型的自动或固定策略解析唯一上游协议。自动模式优先同协议；缺少同协议时，使用模型已配置协议中经过验收的转换目标。
4. 固定模型修订、Provider 配置、协议对应的上游模型、协议和适配器信息，选择该协议地址和 Key，并按配置替换上游模型名。本次请求执行期间不重新解析到另一条路由。
5. 同协议使用透传路径，跨协议使用经验证的适配路径。
6. 记录公共模型、实际上游模型、Provider、入站及上游协议和配置修订，再返回响应。

请求的 `model` 决定本次调用的模型。会话中选定的模型用于启动参数和默认值，不覆盖客户端明确发送的另一个已发布模型。后台请求也必须解析为目录中的模型或已明确配置的 Agent 角色映射，不能使用全局“第一个模型”兜底。

未知或停用的模型返回具体错误。调用方不能通过自带 `x-emdash-*`、Provider ID、地址或 Key，绕过设置中的路由和认证。

Go 进程接收由主进程发布的模型目录和会话绑定快照。Go 负责请求解析和执行；主进程负责配置持久化、会话权限、修订切换和 Agent 生命周期。配置经内部受认证通道发布，不把设置管理能力暴露给 Agent 的会话令牌。

`/v1/models` 和 Agent 模型目录由公共模型目录生成，不直接暴露某个 Provider 的全部物理模型。

## 7. 模型和路由变更

已确认规则：兼容的路由变更在该会话下一轮开始前生效；不兼容的变更保留待生效状态，提示重启或新建会话。

“本轮结束”依据 Agent 的明确空闲状态，并确认该会话没有在途请求。不能把 SSE 连接暂时关闭或两个工具请求之间的空隙当成一轮结束。没有可靠空闲信号时，不自动应用。

| 变更 | 生效规则 |
| --- | --- |
| 只改显示名称 | 界面刷新，不改请求和历史 |
| 同一地址与鉴权方式下轮换 Key | 原请求继续使用已准备的凭据，后续请求采用完整的新凭据配置 |
| 同别名、同上游模型和能力，切到已验证可兼容的 Provider | 等本轮结束后切换，其他仍忙碌会话分别等待自己的边界 |
| 修改上游模型、协议、上下文窗口或工具/推理能力 | 提示重新配置 Agent，通常需要受控重启 |
| 历史中含上游绑定的响应 ID、加密推理、签名或压缩状态 | 保留原绑定；只有适配器验证可恢复时才迁移，否则新建会话 |
| Provider 地址或鉴权范围改变 | 视为破坏性连接变更，不能把新 Key 与旧目标拼接使用；受影响会话提示重启 |
| 停用或删除模型/Provider | 展示受影响会话；在途请求不换路，由用户确认停用策略后阻止后续请求，不切其他线路 |

不能仅凭两个模型的名称和上下文窗口相同就判断历史兼容。首版对未经验证的 Provider 组合默认提示重启。

会话绑定应持久保存已应用的模型/路由修订和必要的非敏感连接快照。旧绑定或凭据作用域不能恢复时，阻止请求并提示恢复配置，不能猜用最新配置。用量保留实际执行修订、入站协议和所选上游协议，不用设置中的最新路由倒推历史。协议映射、自动匹配策略和转换目标的变更同样参与兼容判断；例如新增原生协议会改变已有会话的执行线路，不能在轮内重新挑选。

模型选择变化和模型路由变化分别处理：用户换模型涉及 Agent 的能力目录；管理员把同一模型换到兼容 Provider，通常不需要改变 Agent 面向的网关地址或公共模型名。

## 8. 协议适配与透传

### 8.1 两侧协议分别定义

协议分为 Agent→网关的入站协议和网关→Provider 的上游协议。统一网关可以同时暴露多种入口，并不要求所有 Agent 使用一种请求格式。

Claude Code 在本项目的自定义 API 接入方式下使用 Anthropic Messages，通过 `ANTHROPIC_BASE_URL` 指向网关；这与 [Claude Code 官方网关协议说明](https://code.claude.com/docs/en/llm-gateway-protocol)一致。Codex 的已接入路径使用 Responses。OpenCode、Pi、Oh My Pi 由各自启动适配器选择已经验收的稳定入站协议，日常界面不要求用户选择。

模型的上游协议默认按以下顺序确定：

1. 确定入站协议，并读取该模型在指定 Provider 下已配置的协议映射。实际候选是 Provider 端点与模型协议映射的交集，不能把“Provider 有三种端点”当成“每个模型都支持三种协议”。
2. 自动模式下，同协议存在且满足必要能力时使用它。例如 Claude Code 入站 Messages，就选择该 Provider 的 Anthropic 端点；Codex 入站 Responses，就选择 Responses 端点。
3. 没有可用同协议时，按确定的 SDK 支持顺序选择可用目标；设置中可覆盖转换目标，所选方向、工具及状态能力通过验收后走跨协议路径。否则报告模型不兼容，不自动换 Provider。
4. 固定模式下，只使用设置指定的上游协议。两侧不同则同样必须通过转换检查。
5. 解析结果绑定到会话当前修订和轮次；收到上游 400、401、超时或流中断后，不试着换一种协议重发同一请求。

例如某 Provider 的模型 `code-model-v1` 确实在三种协议下可用，设置只需给它发布一个别名 `coding-main`：

| Agent 入站 | 自动选择的上游 | 处理方式 |
| --- | --- | --- |
| Claude Code / Messages | 该 Provider 的 Anthropic Messages 地址 | 同协议透传及模型别名映射 |
| Codex / Responses | 该 Provider 的 Responses 地址 | 同协议透传及模型别名映射 |
| 配置为 Chat 的 Agent / Chat | 该 Provider 的 Chat Completions 地址 | 同协议透传及模型别名映射 |

每条协议映射使用对应端点、凭据引用和模型名。如果某协议实际对应另一个模型版本、权限或不同的历史状态能力，必须分别校验，不能仅因公开别名相同就认为兼容。

对于支持多种协议的 Agent，先固定其已验证的入站协议，网关按每个请求的模型选择上游。需要改变进程入站协议才能使用另一个模型时，提示受控重启；不在一个正在运行的进程里随物理 Provider 改写配置。无需让所有可配置客户端统一使用 Responses。

设置中的固定上游协议或转换目标不会把 Claude Code 的原生请求格式改成 Responses。只有上游不支持原生协议，才需要处理第 8.2 节的跨协议转换缺口；同协议路线可以独立交付和验收。

### 8.2 固定 SDK 的实际注册情况

项目使用 CLIProxyAPI `v8.0.70-0.20261112185239-1aaf56bc6a0f`。公开 `builtin.Registry()` 和 `HasRequestTransformer`、`HasStreamResponseTransformer`、`HasNonStreamResponseTransformer` 的只读探测结果如下：

| 入站协议 | 上游 Messages | 上游 Responses | 上游 Chat |
| --- | --- | --- | --- |
| Messages | 同协议透传 | 未注册通用直接转换 | 已注册请求、流式及非流式响应转换 |
| Responses | 已注册请求、流式及非流式响应转换 | 同协议透传 | 已注册请求、流式及非流式响应转换 |
| Chat | 已注册请求、流式及非流式响应转换 | 未注册通用直接转换 | 同协议透传 |

注册表检查不等于工具循环或真实供应商兼容性验收。[SDK 扩展接口](https://raw.githubusercontent.com/router-for-me/CLIProxyAPI/1aaf56bc6a0fc6fce19049ba7ae8554c882304a6/docs/sdk-advanced.md)中部分示例仍使用 v6，实施应以固定 v8 的公开 API 和契约测试为准。

SDK 还有 `codex` 专用格式，但其转换会强制设置 `stream`、`store`、推理等字段，不能直接当作任意第三方 Responses 服务的通用转换器。也不默认通过两次转换绕过缺失方向。

对同时提供原生协议的 Provider，优先走同协议路径，不依赖这些缺失转换。只有要开放 Claude Code 访问仅有 Responses 的模型，才必须补齐并验收 Messages→通用 Responses；Chat→通用 Responses 也应在对外开放相应组合前补齐。优先验证 SDK 的公开扩展点能否复用现有转换组件，再决定增加边界适配或升级固定 SDK。没有验证前，不把它标记为可用。

### 8.3 参数、工具和状态

同协议路径保留业务 Header、重复值、查询参数、错误正文和响应字节。只按网关规则处理认证、连接级字段、内部路由信息、Cookie 隔离和显式模型别名。带完整性校验的请求不做未经支持的请求体改写。

跨协议路径必须转换请求和响应，不能承诺字节不变。需要按方向验证系统提示词、文本、工具定义、并行工具调用、工具结果、流式结束与取消、Token 用量和错误。

Claude 会话按所选模型实际使用的上游协议加载模型目录。原生 Anthropic Messages 会话保留提示缓存和实验工具特性，跨协议转换会话在启动时显式关闭这些特性。切换上游协议时，通过 Emdash 模型选择器启动采用对应配置的会话。转换层遇到无法保留的字段时明确拒绝请求。

对图片、推理内容、缓存语义、结构化输出、搜索、`responses/compact`、服务端响应 ID 等能力单独建支持表。没有等价能力时，在启动前禁用该功能或拒绝该模型组合，并给出理由；无法在启动前识别的请求特性，在发送上游前明确拒绝。不能静默删除字段或假造成功的工具结果、响应 ID、压缩结果。

未知字段在同协议路径透传。在跨协议路径中，已经具有验证依据的供应商扩展可以保留；其他未知扩展明确拒绝并指出字段，避免用户误以为它已经生效。

适配器是否注册、必要能力是否支持、凭据是否可用共同决定模型在某 Agent 中的可用状态。模型菜单和请求执行必须使用同一兼容判断。

## 9. 官方登录路径

官方登录继续使用相应 Agent 的账号和原生服务，不经过自定义模型路由。Claude 账号不会默认供 Codex 使用，反之亦然。网关内显式配置的 OAuth 上游也不能改变这个模式的含义。

从网关切到官方登录时，清除 Emdash 本次启动注入的网关地址、能力令牌、模型目录和 provider 参数。不要修改用户 CLI 的全局文件。如果检测到用户自定义 API 覆盖，应指出冲突，使用已有独立官方账号目录或让用户选择迁移；不能把仍指向第三方 API 的运行状态展示为官方登录。

官方登录失败只影响相应模式，不自动消耗网关 Key。网关失败也不自动消耗官方订阅。

## 10. 兼容和迁移

迁移先生成预览，列出公共模型别名、Provider、实际模型和协议的映射。模型名称不能证明两个 Provider 的模型可互换。

1. 从已有 Provider 模型、模型别名和元数据生成公共目录，使用可重入的稳定映射标识。保留可确定的协议映射；只有 Provider 端点、没有模型协议依据时，标为待验证，不自动宣称该模型支持全部协议。
2. 不同 Provider 中的同名模型不自动合并。生成可区分的别名，并允许用户在预览中调整和合并路由。
3. 复用已有 Provider ID 和加密凭据引用，不重新输入 Key，不覆盖官方账号目录。
4. 在 Agent 默认设置中显式选择已发布的网关模型。保留旧默认值，避免隐式改变仍依赖默认值的已运行会话；缺失或歧义引用提示选择，不猜供应商。
5. 已运行和保存的直连会话继续由兼容读取器解释 `modelSource/sourceModel`，普通新建界面不再提供 Provider 直连选择。用户转为网关时显式走受控转换或新建路径。
6. 已有 `gateway:<providerId>` 会话保留它们的 Provider 身份和历史模型解释；完成安全转换前不原地重写成另一条模型路由。
7. 已有用量记录保持原始归因。新增记录增加公共模型、上游模型、Provider 和路由修订字段，历史未知字段保持未知。

迁移完成标记只在配置持久化成功后写入。失败可以重试，不能生成重复目录或留下部分默认值。回退版本仍能读取原记录；存在按新契约创建的会话时，不承诺较旧版本能启动它们，升级/回退提示需要列出这项边界。

## 11. 实现落点和交付顺序

| 部分 | 实现位置和变化 |
| --- | --- |
| 模型领域契约 | `model-gateway/api/` 增加目录、可用性、路由修订和管理操作；浏览器输出不包含 Key |
| Provider 连接 | `model-providers/` 保留地址、协议和凭据，停止把 Provider 模型列表当作第二份发布目录 |
| 启动配置 | `effective-agent-config.ts` 按模式准备环境；`source-launch.ts` 注入一个稳定网关和公共模型目录 |
| 会话选择 | `ModelSourceSelect`、创建及 `restart-conversation.tsx` 改为模式/模型选择，不接收物理 Provider 选择 |
| 网关运行 | `gateway-service.ts` 管理目录发布、能力令牌、绑定修订、待生效变更和恢复 |
| Go 请求层 | `apps/model-gateway/` 按模型别名解析，保留同协议透传，接入经验证的双向转换 |
| Agent 差异 | 插件/启动适配层声明能否接网关、原生协议、目录刷新和模型切换方式；不在通用 UI 中堆分支 |
| Wire 集成 | 沿用所属 slice 的 contract/controller、manifest 和 domain client，不扩展 preload 桥 |

实施顺序：

1. 核对 Provider 端点和模型协议映射，验证 Claude→Messages、Codex→Responses 等同协议路径。同时做需要开放的缺失转换方向契约验证；转换缺口只阻止相应组合，不阻塞多协议 Provider 的同协议路线。若需 SDK 升级，单独列出版本、兼容变化和依赖检查。
2. 增加模型目录、迁移预览和确定性 resolver。第一块可独立验收的改动是“给定别名、入站协议和会话快照，得到唯一 Provider、上游模型和上游协议”，先不切换用户流量。
3. 接入 Go 目录发布和同协议执行，验证按请求 `model` 路由、多个模型/会话并发隔离、修订和错误。
4. 接入协议转换与统一 Agent 目录，验证五个首批 Agent 的 CLI/ACP 路径。完整验证前不对用户宣称任意模型组合都可用。
5. 将新建、默认和切换 UI 改为模式/模型，完成迁移、浏览器交互和真实服务验收。

前面已授权的透传修复保持独立，不借本方案修改协议转换、Provider 选择或历史迁移行为。本轮在保留既有透传修复的基础上实施本方案。

## 12. 验收

| 场景 | 判定依据 |
| --- | --- |
| 新建任一首批 Agent | 接入选择中不列上游 Provider；网关下只选公共模型 |
| 同一个模型绑定多协议 Provider | Claude 选 Anthropic、Codex 选 Responses；使用各自端点、Key 和物理模型名，不经过跨协议转换 |
| Provider 支持多协议但模型仅支持一种 | 其他协议不被误标为原生可用；仅在 SDK 支持且适配验收通过时转换 |
| 同协议上游报错 | 返回原错误，不换协议或 Provider 隐式重放 |
| 两个模型绑定不同 Provider | 只改请求 `model` 即命中对应上游；不被会话默认值覆盖 |
| 同一别名用于 Claude 和 Codex | 输入/输出符合各客户端原生协议，工具调用及下一轮工具结果都能完成 |
| 同协议自定义参数 | 请求体除显式模型映射外保持原字节，错误和业务元数据返回正确 |
| 跨协议不支持的字段/能力 | 有明确拒绝，不能静默忽略后继续计费执行 |
| 运行中修改兼容路由 | 当前轮所有请求保持原快照，空闲后按确认策略切换 |
| 修改模型能力或历史绑定不兼容 | 提示重启/新建，不尝试把服务端状态送给另一上游 |
| 网关/官方切换 | 环境、认证和模型目录相互隔离，失败不回退到另一种付费来源 |
| Provider 缺 Key、过期、删除或网关重启 | 只影响相关路由；显示可定位错误，不影响其他有效模型 |
| 迁移失败与重复执行 | 原会话、凭据和账本保留，无重复模型和错误默认值 |
| 模型目录刷新 | 原生 TUI/ACP 只展示适配器确实能加载和选择的模型 |

测试分层：resolver/schema 单元测试；实际 Go 子进程与三个模拟协议上游的契约测试；真实 CLI/ACP 客户端针对模拟上游的工具循环；设置和选择器浏览器测试；最后使用有效凭据完成至少一条真实服务链路。mock 成功不能替代真实服务验收。

固定 SDK 的注册表相关测试已通过，只证明本方案引用的探测接口和注册行为可用。功能实现及各层验证结果记录在交付说明中；真实供应商验证与模拟上游测试分别报告，不混称为完整线上验收。

## 13. 已确认的决定

建议采用“模型目录为唯一发布源、会话只选接入方式和模型、一个别名绑定一个 Provider，并按入站协议确定具体路由”的方案。

第 7 节的路由更新策略已经确认：兼容变更在下一轮自动应用，不兼容变更提示重启。整体方案及 SDK 转换优先复用的实现方向也已获用户确认，进入实施与验收。

跨协议支持是实现目标的一部分，同协议透传保证不能直接外推到转换路径。真实工具循环是每条开放路线的验收门槛；缺失的通用 Responses 转换只作为依赖它的组合的开放门槛。
