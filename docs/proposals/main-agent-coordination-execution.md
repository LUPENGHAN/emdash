## 1. 执行顺序与交付物

先交付默认强度和明确的任务路由，再完成一个项目的真实派活闭环，随后开放跨项目、管理文档和 Git 协作。恢复能力随各步骤实现，最终集中做故障验收。

| 顺序 | 工作包 | 用户可见结果 | 依赖 |
| --- | --- | --- | --- |
| P1 | 默认模型强度 | 设置可保存默认 effort，普通新会话实际使用 | 无 |
| P2 | 派活配置和任务路由 | 派活可指定供应商、模型名、effort，不影响其他会话 | P1 |
| P3 | 后台派活链路 | 创建和启动任务不依赖目标页面已打开 | P2 |
| P4 | 项目主 Agent 与结果闭环 | 项目下有固定主 Agent，能派活并收到可检查结果 | P3 |
| P5 | 跨项目协作 | 一个主 Agent 向多个仓库派活，并集中收到结果 | P4 |
| P6 | 管理文档 | 主 Agent 页面可维护独立管理分支中的文档 | P4；跨项目场景验收依赖 P5 |
| P7 | PR 与上游同步 | 明确 PR 目标，安全同步本地基线，保留任务分支 | P5、P6 |
| P8 | 综合验收与交付 | 重启、失败、迁移、多窗口及支持的远程组合有验证证据 | P1–P7 |

P1 可以独立交付。P1–P4 对应设计方案的单项目阶段，P5、P6、P7 分别对应跨项目、文档和 Git 阶段。本文不把阶段完成等同于全部功能完成。

贯穿验收使用同一个案例：在 Emdash 主 Agent 中维护方案，给 SDK 仓库派任务 A，再给调用方仓库派依赖 A 的任务 B；A 的结果通过检查后 B 才启动。两个任务可以使用不同 Agent、供应商、模型和 effort。结果留在各自任务分支，需要时向明确指定的组织仓库开 PR。

#### 批次 1：文档能编辑，也能成为明确的任务输入

用户打开主 Agent 的“文档”，创建、编辑并保存方案，再选择其中几份派给任务 Agent。

1. 在 `coordination/api` 定义文档工作区、相对路径和版本契约，Wire 控制器调用协调服务。协调域决定文档位置与访问权限，目标 Host 的文件／Git runtime 负责读写；renderer 不直接访问桌面文件系统。
2. 在主 Agent 页面增加文档标签，复用文件树、编辑器和保存机制。协调身份绑定明确的文档工作区，切换主会话不改变文档位置。打开文档只准备资源，不自行发送模型请求。
3. 增加 MCP 管理文档读取能力。先校验调用者与目标，再解析路径；拒绝越界、`.git` 和借符号链接读出工作区。远程任务获得内容和版本，不能只返回桌面绝对路径。跨项目关联不自动授予全部文档权限。
4. 扩展 `create_task` 的可选文档引用，兼容省略字段的历史调用。首次派发持久化选中文档的路径、来源、版本和内容快照；请求重试、等待依赖及重启均使用同一快照。已有请求不能因源文档修改而换输入。
5. 已提交文档按完整提交 ID 读取，并验证提交属于该管理历史；未提交文档返回内容版本，修改后旧版本读取明确报失效。任务已经冻结的内容仍可追溯，不把最新内容冒充旧版本。

改动集中在 `coordination/api`、`node/coordinator-documents.ts`、协调服务及页面，`agent-control/api`／MCP／派发记录，以及 bootstrap 的 Host 能力接线。持久字段走版本化 schema，未知未来版本拒绝覆盖。

完成证据：隔离 Electron 中创建并保存文档，重启后能打开；派活后修改原文档，任务上下文仍是选定版本；未经授权的读取被拒绝。代码任务差异不含管理文档，管理历史与代码基线无共同祖先。

第一块独立提交先完成文档 Wire 和真实编辑保存，再提交受控读取及派活快照，避免把整个 P6 堆成一个提交。

#### 批次 2：迁移和文档 Git 操作

1. 先识别历史主 Agent 的代码 checkout、管理资料和会话引用，记录来源与目标。只迁移明确属于主 Agent 管理的文档；README、公开 API 文档等产品文档仍归代码任务。
2. 通过 workspace registry 准备独立管理工作区，按“复制 → 校验 → 保存迁移状态 → 切换文档引用”执行。中断后从持久步骤重试；原分支、原文件和会话历史保留，不静默改写活跃会话的工作目录。
3. 文档存储绑定与主会话绑定分别保存。旧会话仍能查看，主会话切换不丢任务关系；文档存储项目不可用时显示原因，不能悄悄转存另一个仓库。
4. 空 Git 仓库允许先建立管理文档历史；没有代码基线时禁止代码分支派活。非 Git 目录保留可用的主 Agent 对话入口，Git 功能标为不适用；需要版本化文档时显式选择关联 Git 仓库，不自动初始化原目录。
5. 复用 Git runtime 提供文档本地提交，提交范围局限管理工作区。推送前明确显示个人 fork 和管理分支；未配置目标时保存在本地，创建主 Agent 不自动推送。
6. UI 和后台共同阻止管理分支作为代码任务基线或代码 PR 来源，覆盖完整 ref 和远端引用。该限制不只依赖分支选择器过滤。

完成证据：迁移在复制中、校验后、引用切换前后分别中断并恢复，文档与历史均未丢失；本地 bare fork 验证文档只推送到明确目标；普通代码 PR 不包含管理文档；空仓库和非 Git 项目有可用入口及准确状态。

#### 批次 3：已有派活链路的恢复收尾

依赖启动、用户消息优先和待处理入口已实现，本批补它们在完整退出和并发情况下的保证。

1. 提供按稳定任务 ID 显式重试失败派发的入口。后台验证当前负责人和权限，沿用原请求键、资源 ID、配置与文档快照；切换主会话或接管后仍能重试，不重新建任务。
2. 在任务保存、worktree 创建、会话启动、结果入库和接收确认之间注入中断。恢复从持久步骤继续；已经无法判断是否执行的消息保留待处理，不自动重放。
3. 两个窗口同时检查同一结果或接管同一任务时，按预期负责人和结果版本做原子校验。过期决定返回冲突，不能覆盖另一窗口已经提交的决定。
4. 完整退出并重启 Electron，核对等待依赖、取消、检查决定、待处理消息、文档绑定和主会话绑定。页面关闭或 renderer 退出不能成为后台派发的必要条件。

完成证据：恢复前后任务／worktree／会话数量不增加，负责人和输入快照不漂移；投递状态不明的消息可见；旧主会话不能继续确认新接收者的结果。每个故障点保留状态与执行次数记录。

#### 批次 4：明确 PR 的源和目标

1. 扩展已有 PR 操作，明确源任务、源分支、push remote、目标仓库和目标分支。默认值由对应项目设置域解析，不写死 `origin` 或 `main`。
2. 主 Agent 可为负责的任务创建 PR；任务 Agent 可为自己的任务创建。后台用调用身份校验源任务，目标解析失败时不能改投另一个仓库。
3. 请求重试先查询匹配 PR；找到一条返回原链接，存在歧义则返回候选。管理分支被拒绝，创建 PR 不触发自动合并。

完成证据：契约测试覆盖“个人 fork 的任务分支 → 组织仓库 develop”，验证权限、重复请求和歧义；实际 Git 推送用本地 bare 仓库，托管平台创建使用可控测试接口，不向真实组织发送测试 PR。

#### 批次 5：安全跟进上游

1. 用项目的 `defaultBranch`、`baseRemote` 解析上游和本地代码基线。连接恢复、创建代码任务前，以及已有集成观察到相关 PR 合并时触发；同仓库串行、合并重复事件，不增加持续 API 轮询。
2. fetch 后检查祖先关系和 checkout 状态，只执行安全快进。不能直接改 ref 绕过已检出工作区；脏目录、分叉、远端历史改写及不可安全更新的 checkout 返回具体原因。
3. 同步不改任务分支、管理分支，也不自动 rebase。按项目配置运行同步后检查，保存前后提交与输出；检查失败暂停基于失败状态的自动派活，不静默硬重置。
4. 显示上次检查时间、结果和离线状态。网络失败但有有效本地基线时可继续并记录状态；从未建立有效基线则阻止创建。同步本地与推送 fork 主分支分别配置。

完成证据：本地 bare 上游／fork 覆盖快进、脏目录、分叉、远端改写、离线及检查失败；全过程核对已有任务分支提交 ID 不变。没有验证命令时只报告 Git 同步成功。

#### 批次 6：整体验收与交付

从干净隔离 profile 真实启动 Electron，串起“保存默认配置 → 主 Agent 文档 → 跨仓库依赖派活 → 执行与结果检查 → 明确 PR 目标 → 上游更新 → 本地基线同步”，再完整退出重启。验收由开发侧执行，保留界面、Git、持久状态和请求记录。

默认 effort 必须核对以下行为：

- 本次显式值 → 主 Agent 派活默认 → 所选 Agent 设置默认 → 模型／适配器默认；明确选择跟随适配器默认也要保留其语义。
- 普通会话、主 Agent 和任务都使用同一有效值解析，界面显示值与 CLI／ACP 参数、网关上游请求相符。
- 排队后修改全局默认不改变任务快照；不支持的组合明确报错，不静默降级或切换登录方式。用量账本仍归属实际任务及路由。

模拟 CLI／ACP、可控上游、真实 Agent 和远程 Host 分别列版本与证据。旧 Host 不支持管理工作区或队列能力时明确拒绝或显示限制，不退回普通代码 worktree。环境缺失的组合列为未验证，不能用模拟结果宣称真实环境通过。

每批运行相关测试、类型检查和 lint；全部功能收尾后从根目录执行 `pnpm run format`、`pnpm run lint`、`pnpm run typecheck`、`pnpm run test`。只对改动或失败涉及的检查重跑。最终记录完成范围、提交、迁移和支持矩阵，以及每项剩余限制。

所有验收使用独立数据库、应用配置、临时仓库和 worktree 根目录，不触碰生产数据，不使用 Emdash terminal。开发本功能按约定直接提交分支；实际推送、打包与发布分别遵守用户明确指令。

## 3. P1：设置中的默认模型强度

先形成一个可以独立使用的结果：在设置中选好模型和默认 effort，创建普通会话时实际生效，应用重启后保留。

实施步骤：

1. 扩展 Agent 有效默认配置，保存可选默认 effort；未设置表示跟随模型／适配器默认。具体字段沿用现有设置域，不额外建立全局强度表。
2. 提取共享的启动选择解析函数。输入包含 Agent、host、接入方式、模型选择、显式覆盖和默认配置；输出包含有效值、来源、配置版本和明确错误。
3. 从 Agent 插件和模型能力解析可用强度，兼容已有 Codex 专用配置。具体默认值不兼容时返回错误，不能静默降级。
4. 在设置的 Agent 默认模型旁增加默认强度控件；切换模型时重新校验，支持恢复默认。
5. 普通创建会话、创建任务中的初始会话、主 Agent 和后续 MCP 派活使用同一个解析入口。前端可以预览，后台负责最终校验和冻结有效配置。
6. 在 CLI 和 ACP 边界应用解析结果，保留历史空值行为，不修改已运行会话或已解析的排队任务。

- `features/agents/api/browser/use-agent-settings.ts` 及对应后端设置接口。
- `features/model-providers/browser/providers-settings-page.tsx`、`api/browser/use-model-source.ts`。

## 4. P2：派活配置与任务级模型路由

统一派活输入：`agent`、`connection`、`supplier_id`、`model`、`effort`。原有省略字段的调用保持可用。

实施步骤：

重点位置：`agent-control/node/mcp-tools.ts`、`model-providers/api/node/source-launch.ts`、`model-gateway/api/`、`model-gateway/node/` 及实际持有会话路由的服务。必要的网关协议扩展与调用方一起验证，不新增直连供应商捷径。

完成条件：同一供应商的两个模型和两个不同供应商可以分别派活；请求使用正确上游模型及 effort；公共别名、默认配置和其他会话不被覆盖；网关账本仍能归属任务；停用供应商后不会回退到官方登录。

建议提交主题：`feat(model-gateway): support task-scoped model routing`。

## 5. P3：不依赖前台的派活

先把派活变成可验证的后台操作，再接主 Agent UI。

实施步骤：

1. 提供后台派发操作，接收已认证调用者、明确目标项目、任务说明、基线和模型选择；所有输入在后台校验。
2. 按目标项目建立或取得 attachment，调用已有任务与 workspace 创建服务；不用前端 store 判断项目是否可操作。
3. 默认从目标项目代码基线创建。需要从某个任务分支继续时显式指定，管理分支永不成为隐式代码基线。
4. 持久化 `request_id` 和稳定任务、workspace、会话 ID，记录准备、资源创建、会话启动等执行步骤。相同请求重试返回同一结果。
5. 将已有任务创建步骤与会话启动组合起来；会话记录存在不代表进程已启动。启动失败保留资源并可从失败步骤重试。
6. 自动派活操作不再经 renderer dispatcher；需要用户交互的原有操作仍走对应交互路径。

主要复用 `tasks/node/operations/createTask.ts`、会话域启动服务、`workspace-registry` 和 host runtime。新增协调后台 API 使用 typed Wire，通过 manifests 注册。

完成条件：目标项目页面未打开也能创建并启动；相同请求执行两次只有一个任务；在 worktree 建立后注入中断，恢复不会创建第二个分支；模型配置失败不会启动错误会话；无 renderer 时后台行为可测试。

建议提交主题：`feat(agent-control): dispatch tasks through backend services`。

## 6. P4：项目主 Agent 与结果闭环

这是第一批完整产品体验的交付点。

实施步骤：

1. 建立协调者记录、项目默认绑定、任务负责关系、派发记录和结果事件。为项目默认绑定及幂等请求加唯一约束；迁移与恢复都能重复执行。
2. 协调者绑定显式角色的运行容器，复用会话和 workspace。更新任务类型消费者，排除普通任务统计和常规归档动作，避免通过任务名称识别角色。
3. 项目创建事件幂等建立主 Agent；升级时补齐记录，资源按需准备，不自动为所有项目启动模型进程。
4. 在项目下面增加固定主 Agent 行，注册主 Agent 页面及导航。普通任务、置顶、项目排序和分组行为保留。
5. 提供任务说明和任务引用列表，支持主 Agent 派活；普通任务的说明只有一个权威来源。
6. 增加提交结果能力，保存分支／提交、摘要、验证证据和未解决项。结果进入待检查，进程空闲或退出不自动置为完成。

完成条件：临时项目创建后能直接进入主 Agent，派出任务、查看真实改动并收到结果；关闭重开页面无影响；主会话重启后任务关系和未读结果仍在；普通任务列表没有管理容器；同一结果重投不会重复派活。

当前草稿的收尾清单：

1. 核对管理运行容器在普通任务列表、置顶、统计、MCP 查询、归档和删除入口中的行为；固定主 Agent 不被当作普通任务处理。
2. 主 Agent 自身配置与派活默认配置分别展示。派活表单按 Agent／模型能力提供 effort 选项，显示继承值和来源，后台复核兼容性。
3. 补齐结果提交、重复投递、并发提交、应用重启和损坏记录的测试。结果按版本检查，旧结果的重试不能重新打开已接受任务。
4. 核对 ACP 忙时排队、用户消息优先和事件确认；PTY 无法可靠确认消费时保留待处理提示。投递成功与主 Agent 已确认消费分别记录。
5. 在隔离 Electron 中完成一次“打开主 Agent → 派活 → 执行任务 → 提交结果 → 检查结果”的模拟流程，保存界面、任务分支和事件记录。模拟 Agent 与真实模型调用的证据分别标明。
6. 修复相关测试与类型检查后提交 P4。管理分支独立历史和文档页仍由 P6 完成，不能用阶段性代码基线分支冒充文档隔离。

建议按后端与 UI 拆成聚焦提交，主题围绕 `feat(coordination)`；每个提交写明已经验证到的链路。

## 7. P5：跨项目协作

1. 扩展项目发现和任务查询，区分调用来源、目标项目、关联项目与操作授权。使用稳定 ID，不接受任意路径代替项目身份。
