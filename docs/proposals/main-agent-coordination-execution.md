## 1. 执行顺序与交付物

先交付默认强度和明确的任务路由，再完成一个项目的真实派活闭环，随后开放跨项目、管理文档和 Git 协作。恢复能力随各步骤实现，最终集中做故障验收。

| 顺序 | 工作包 | 用户可见结果 | 依赖 |
| --- | --- | --- | --- |
| P1 | 默认模型强度 | 设置可保存默认 effort，普通新会话实际使用 | 无 |
| P2 | 派活配置和任务路由 | 派活可指定供应商、模型名、effort，不影响其他会话 | P1 |
| P3 | 后台派活链路 | 创建和启动任务不依赖目标页面已打开 | P2 |
| P4 | 项目主 Agent 与结果闭环 | 项目下有固定主 Agent，能派活并收到可检查结果 | P3 |
| P5 | 跨项目协作 | 一个主 Agent 向多个仓库派活，并集中收到结果 | P4 |
| P6 | 管理文档 | 主 Agent 页面可维护独立管理分支中的文档 | P4；跨项目场景验收依赖 P5 |
| P7 | PR 与上游同步 | 明确 PR 目标，安全同步本地基线，保留任务分支 | P5、P6 |
| P8 | 综合验收与交付 | 重启、失败、迁移、多窗口及支持的远程组合有验证证据 | P1–P7 |

P1 可以独立交付。P1–P4 对应设计方案的单项目阶段，P5、P6、P7 分别对应跨项目、文档和 Git 阶段。本文不把阶段完成等同于全部功能完成。

#### 第一批：安全清理与中断残留

目前固定提交的验证执行器会保存 workspace／run 回执，检查目录保留用于诊断。现有普通 `deleteWorktree` 会先停用工作区、处理 teardown，再强制移除，不能直接作为验证目录的清理路径。

1. 在 Host workspace registry 增加受限的清理操作，输入携带已保存的工作区身份、父仓库、路径、分支及固定提交；在已有工作区互斥与 Git 写入通道中再次验证。不得把来自页面的任意路径直接交给删除命令。
2. 只清理结果已持久保存且执行已结束的检查。活动脚本、会话、身份或 HEAD 变化，以及修改、未跟踪文件和 ignored 文件均须阻止清理并给出原因。不运行项目 teardown，不使用强制删除。Git 的非强制 worktree remove 仍可能移除 ignored 文件，必须自行检查。
3. 项目域持久保存清理阶段和结果，typed Wire 提供操作，项目基线设置显示入口与拒绝原因。清理目录后保留检查提交、命令版本、退出码及脱敏输出；再次读取历史证明不依赖目录仍存在。
4. 删除响应丢失时按原身份恢复；“注册记录不存在且路径已不存在”可以确认已清理，路径仍存在则拒绝猜测删除。对 SIGKILL 留下的私有 candidate ref，先建立可恢复的所属操作身份，再清理确认不再运行的本操作资源；不扫描删除其他进程可能使用的 ref。

验收覆盖干净目录成功、脏文件及 ignored 文件拒绝、运行中拒绝、路径／HEAD 变化拒绝、响应丢失恢复、应用强制退出后恢复。核对任务分支、管理分支、用户文件和历史检查回执保留。清理能力可独立完成、验收并提交，是第一块实施改动。

#### 第二批：默认模型强度与派活配置全链路

设置中的 Agent 默认配置放在同一处：接入方式、模型、默认 effort。提供“跟随模型／Agent 默认”，具体档位来自所选 Agent、模型和协议组合的能力。主 Agent 自身会话配置与派活默认分别保存。

有效 effort 按以下顺序解析：

```text
本次会话／任务显式值
  → 主 Agent 派活默认（仅派活时）
  → 所选 Agent 的设置默认
  → 模型／适配器默认
```

普通会话和主 Agent 自身跳过派活默认。未设置或明确选择跟随默认才继续继承；已保存的具体值不兼容时报错。普通使用选择公共模型别名即可；高级派活可覆盖 Agent、接入方式、供应商、实际模型名和 effort。供应商与协议配置继续复用模型域，任务级覆盖不改写全局别名。

沿“设置 → 主 Agent 派活默认 → 后台解析与持久快照 → CLI／ACP 启动 → 会话网关路由 → 上游请求 → 持久账本与统计展示”逐项核对。界面负责展示和预览，后台拥有最终解析与校验；启动、重试和用量归属都消费同一有效配置。Claude 等 Agent 的入口协议由适配器约束，协议转换能否保留模型及 effort 以可控请求验证。

验收包含默认值保存重启、清除覆盖、普通会话与派活分别生效、两任务选择不同配置，以及排队后修改全局默认再重启／重试。已解析任务保留原快照；显式不兼容配置不能静默降级。分别捕获 CLI 参数、ACP 配置、模拟上游请求和账本归属，不能只证明表单能保存。

#### 第三批：并发与故障恢复

1. 在派发保存、worktree 创建、会话启动、结果保存、消息投递和确认之间注入中断；按稳定请求和资源 ID 恢复，逐一核对创建与执行次数。
2. 两个真实窗口同时派活重试、接管、接受结果和编辑文档，使用负责人及版本条件只接受有效决定；另一窗口显示冲突并刷新，不能后写覆盖先写。
3. 覆盖等待中接管、依赖取消、用户消息优先、主会话切换、关闭目标页面和完整应用重启。负责人变更后，旧身份不能继续控制任务。
4. 无法确认消息是否已经执行时保存可见待处理状态，不自动重放。迁移前后的主会话历史内容、文档版本与任务输入快照也须检查，不只比较 ID。

验收记录每个故障点的持久阶段、调用次数、资源数量和最终结果。以真实 Electron 双窗口及持久状态核对补充服务测试，不能仅用两个测试函数调用替代窗口恢复。

#### 第四批：适配器、远程与版本兼容

先盘点可用的真实 CLI／ACP 和隔离远程 Host，再建立“Agent／版本、接入方式、传输方式、Host 版本、模型／effort、验证结果”的支持矩阵。模拟协议通过、真实进程通过和真实上游通过分别记录。

远程核对目标 Host 的工作路径、凭据引用、网关可达性、文档内容传递及断连恢复；不能向远程任务传桌面 loopback 地址或仅桌面有效的本地路径。旧 Host 不支持管理工作区、固定提交操作、队列语义或清理能力时明确报告限制，不静默换用改变语义的路径。PR 多账号场景须核对源仓库推送账号和目标仓库 API 账号。

有环境的组合执行验证；缺少真实账号、模型或远程环境的组合保留未验证状态，不能拿模拟结果填成支持。遇到必须补充的条件时指出具体组合及缺失条件，其余验收继续推进。

#### 第五批：完整隔离验收与交付

用同一个用户场景串起所有能力：

1. 保存 Agent 默认模型和 effort，打开 Emdash 项目主 Agent，维护管理文档。
2. 向 SDK 仓库派任务 A，使用默认配置；向调用方仓库派依赖 A 的任务 B，显式覆盖供应商、模型和 effort，并附指定版本的文档。
3. 等待期间修改默认设置并完整重启。A 的结果通过检查后 B 才启动，B 仍使用派活时冻结的配置和文档。
4. 结果留在各自任务分支。由主 Agent 或任务 Agent 向明确的组织仓库／分支开 PR；模拟创建响应丢失和重试，最终只有一个对应 PR。
5. 上游产生或合并提交后，本地基线安全快进并执行配置的验证命令；脏目录、分叉、历史改写和检查失败显示阻止原因。已有任务和管理分支 OID 不变，个人 fork 主分支没有隐式推送。
6. 清理已结束的检查目录，重启后仍可追溯检查记录、任务关系、文档和 PR；核对用量账本及统计归属。

所有验收使用独立数据库、应用配置、临时仓库和 worktree 根目录，不触碰生产数据，不使用 Emdash terminal。可控模型与托管接口用于重复故障实验，真实外部请求只在已授权且可用的环境中验证。

每批运行相关测试、类型检查、lint 和格式检查，按可独立验证的行为直接提交 `feat/multi-agent`。最终从根目录运行 `pnpm run format`、`pnpm run lint`、`pnpm run typecheck`、`pnpm run test`，失败定位修复后只重跑相关检查。提交交付记录包含完成范围、提交、迁移、截图、脱敏请求证据和支持矩阵。实际项目推送、打包、发布仍按各自明确指令执行。

## 3. P1：设置中的默认模型强度

先形成一个可以独立使用的结果：在设置中选好模型和默认 effort，创建普通会话时实际生效，应用重启后保留。

实施步骤：

1. 扩展 Agent 有效默认配置，保存可选默认 effort；未设置表示跟随模型／适配器默认。具体字段沿用现有设置域，不额外建立全局强度表。
2. 提取共享的启动选择解析函数。输入包含 Agent、host、接入方式、模型选择、显式覆盖和默认配置；输出包含有效值、来源、配置版本和明确错误。
3. 从 Agent 插件和模型能力解析可用强度，兼容已有 Codex 专用配置。具体默认值不兼容时返回错误，不能静默降级。
4. 在设置的 Agent 默认模型旁增加默认强度控件；切换模型时重新校验，支持恢复默认。
5. 普通创建会话、创建任务中的初始会话、主 Agent 和后续 MCP 派活使用同一个解析入口。前端可以预览，后台负责最终校验和冻结有效配置。
6. 在 CLI 和 ACP 边界应用解析结果，保留历史空值行为，不修改已运行会话或已解析的排队任务。

重点检查位置，路径相对 `apps/emdash-desktop/src/core/`：

- `features/agents/api/browser/use-agent-settings.ts` 及对应后端设置接口。
- `features/model-providers/browser/providers-settings-page.tsx`、`api/browser/use-model-source.ts`。
- `features/conversations/api/provider-settings.ts`、`node/provider-settings-service.ts`、创建会话与启动入口。
- `primitives/tasks/api/task-config.ts` 与会话配置 schema。
- Agent 插件的能力和 CLI／ACP 配置适配；通用默认解析不放进供应商专用插件。

完成条件：保存和重启恢复通过；普通会话的有效 effort 与设置一致；明确覆盖优先；缺省值保持历史行为；CLI／ACP 支持路径实际收到值；不支持的组合给出明确错误。

建议提交主题：`feat(agents): add default model effort settings`。

## 4. P2：派活配置与任务级模型路由

统一派活输入：`agent`、`connection`、`supplier_id`、`model`、`effort`。原有省略字段的调用保持可用。

实施步骤：

1. 在 `agent-control/api` 和 MCP schema 中定义输入和有效配置返回值，使用模型供应商的稳定 ID。
2. 复用 P1 解析逻辑，接入优先级：本次显式值、主 Agent 派活默认、设置默认、模型／适配器默认。
3. 模型与网关域增加会话范围的供应商／模型绑定。只传公共别名时保持现有模型目录路径；显式供应商和模型名时使用该绑定。

重点位置：`agent-control/node/mcp-tools.ts`、`model-providers/api/node/source-launch.ts`、`model-gateway/api/`、`model-gateway/node/` 及实际持有会话路由的服务。必要的网关协议扩展与调用方一起验证，不新增直连供应商捷径。

完成条件：同一供应商的两个模型和两个不同供应商可以分别派活；请求使用正确上游模型及 effort；公共别名、默认配置和其他会话不被覆盖；网关账本仍能归属任务；停用供应商后不会回退到官方登录。

建议提交主题：`feat(model-gateway): support task-scoped model routing`。

## 5. P3：不依赖前台的派活

先把派活变成可验证的后台操作，再接主 Agent UI。

实施步骤：

1. 提供后台派发操作，接收已认证调用者、明确目标项目、任务说明、基线和模型选择；所有输入在后台校验。
2. 按目标项目建立或取得 attachment，调用已有任务与 workspace 创建服务；不用前端 store 判断项目是否可操作。
3. 默认从目标项目代码基线创建。需要从某个任务分支继续时显式指定，管理分支永不成为隐式代码基线。
4. 持久化 `request_id` 和稳定任务、workspace、会话 ID，记录准备、资源创建、会话启动等执行步骤。相同请求重试返回同一结果。
5. 将已有任务创建步骤与会话启动组合起来；会话记录存在不代表进程已启动。启动失败保留资源并可从失败步骤重试。
6. 自动派活操作不再经 renderer dispatcher；需要用户交互的原有操作仍走对应交互路径。

主要复用 `tasks/node/operations/createTask.ts`、会话域启动服务、`workspace-registry` 和 host runtime。新增协调后台 API 使用 typed Wire，通过 manifests 注册。

完成条件：目标项目页面未打开也能创建并启动；相同请求执行两次只有一个任务；在 worktree 建立后注入中断，恢复不会创建第二个分支；模型配置失败不会启动错误会话；无 renderer 时后台行为可测试。

建议提交主题：`feat(agent-control): dispatch tasks through backend services`。

## 6. P4：项目主 Agent 与结果闭环

这是第一批完整产品体验的交付点。

实施步骤：

1. 建立协调者记录、项目默认绑定、任务负责关系、派发记录和结果事件。为项目默认绑定及幂等请求加唯一约束；迁移与恢复都能重复执行。
2. 协调者绑定显式角色的运行容器，复用会话和 workspace。更新任务类型消费者，排除普通任务统计和常规归档动作，避免通过任务名称识别角色。
3. 项目创建事件幂等建立主 Agent；升级时补齐记录，资源按需准备，不自动为所有项目启动模型进程。
4. 在项目下面增加固定主 Agent 行，注册主 Agent 页面及导航。普通任务、置顶、项目排序和分组行为保留。
5. 提供任务说明和任务引用列表，支持主 Agent 派活；普通任务的说明只有一个权威来源。
6. 增加提交结果能力，保存分支／提交、摘要、验证证据和未解决项。结果进入待检查，进程空闲或退出不自动置为完成。
7. 通过持久事件队列唤起或通知主 Agent，忙时排队，按事件 ID 去重。无法确认投递的 PTY 路径保留待处理，不强行向活跃输入注入消息。

这一工作包引入 `features/coordination/` slice。数据库通过项目规定的生成流程修改，主 Agent UI 通过 contributions 注册。文档页在 P6 前保持未开放，不能显示已完成的管理分支能力。

完成条件：临时项目创建后能直接进入主 Agent，派出任务、查看真实改动并收到结果；关闭重开页面无影响；主会话重启后任务关系和未读结果仍在；普通任务列表没有管理容器；同一结果重投不会重复派活。

当前草稿的收尾清单：

1. 核对管理运行容器在普通任务列表、置顶、统计、MCP 查询、归档和删除入口中的行为；固定主 Agent 不被当作普通任务处理。
2. 主 Agent 自身配置与派活默认配置分别展示。派活表单按 Agent／模型能力提供 effort 选项，显示继承值和来源，后台复核兼容性。
3. 补齐结果提交、重复投递、并发提交、应用重启和损坏记录的测试。结果按版本检查，旧结果的重试不能重新打开已接受任务。
4. 核对 ACP 忙时排队、用户消息优先和事件确认；PTY 无法可靠确认消费时保留待处理提示。投递成功与主 Agent 已确认消费分别记录。
5. 在隔离 Electron 中完成一次“打开主 Agent → 派活 → 执行任务 → 提交结果 → 检查结果”的模拟流程，保存界面、任务分支和事件记录。模拟 Agent 与真实模型调用的证据分别标明。
6. 修复相关测试与类型检查后提交 P4。管理分支独立历史和文档页仍由 P6 完成，不能用阶段性代码基线分支冒充文档隔离。

建议按后端与 UI 拆成聚焦提交，主题围绕 `feat(coordination)`；每个提交写明已经验证到的链路。

## 7. P5：跨项目协作

实施步骤：

1. 扩展项目发现和任务查询，区分调用来源、目标项目、关联项目与操作授权。使用稳定 ID，不接受任意路径代替项目身份。
2. 创建任务接受目标项目，发送消息通过目标会话解析实际所属任务。授权范围内的常规派活不逐次弹确认。
3. 子任务继承明确的可用权限，不能扩大调用者权限；不同 host 的路径、凭据和运行时由目标项目决定。
4. 增加按需显示的跨项目主 Agent 入口及关联项目设置。项目主 Agent 也可以跨项目派活，入口不被迫迁移。
5. 实现一个任务一个负责者、显式接管、简单依赖和阻塞原因。前置任务通过检查后再启动依赖任务。

## 8. P6：管理分支与文档

实施步骤：

1. 通过 Git runtime 与 workspace registry 建立独立管理分支和 worktree，保存位置与分支绑定。独立历史能力若需新增 Git 操作，只在 Git runtime 内实现。
2. 将阶段性管理目录迁入管理 worktree，核对文件内容后更新引用；失败保留原目录供恢复，不能因迁移中断丢文档。

完成条件：管理文档可编辑、保存、恢复；任务相对代码基线的差异不含管理文档；迁移中断可重试；跨项目主 Agent 不生成多份互相冲突的 docs。

## 9. P7：PR 和上游同步

实施步骤：

1. 复用 PR 集成，明确源任务、分支、push remote、目标仓库和分支，工具返回真实目标。创建请求重试时先识别对应已有 PR。
2. 项目配置保存基线和上游来源；不硬编码 `main` 或 `origin`。
3. 接入项目连接恢复、创建任务前和已有 PR 合并观察事件，去重后执行 fetch、分叉及 checkout 状态检查、安全快进和状态刷新。
4. 检测已检出基线、脏工作区、本地分叉和远端历史改写；停止不安全写入，保留任务分支。
5. 按已有项目配置运行同步后检查，失败记录前后提交和输出，停止基于失败状态继续自动派活；没有检查命令时明确只验证 Git 同步。
6. UI 展示最后检查时间和结果。同步本地基线与推送个人 fork 主分支分开，后者只在明确配置时执行。

完成条件：用临时 bare 上游、fork 和工作仓库验证快进、分叉、脏工作区与恢复；同步前后任务分支提交 ID 保持不变；PR 契约可以指向组织仓库；没有自动合并、强推或向真实组织仓库发送测试 PR。

建议分别提交 PR 目标支持与基线同步，避免一个提交同时改动两条高风险链路。

## 11. 进度与停止条件

接续顺序以第 1.2 节的五批为准。每批完成后记录用户可完成的操作、代码提交、实际运行的检查、隔离启动证据和剩余项，再进入下一批。第 12 节保留历史过程；其中阶段性的“尚未实现”不替代第 1.1 节的现态。
