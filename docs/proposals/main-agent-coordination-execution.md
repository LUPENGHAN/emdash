# 主 Agent 协作执行方案

状态：用户已授权完整实施，目标保持 P1–P8 全部完成并真实启动应用进行隔离模拟验收。实施进度见文末记录。

产品规则以 [主 Agent 与跨仓库任务协作方案](main-agent-coordination.md) 为准。本文规定开发顺序、改动边界和每一步的完成条件。用户新增的默认模型强度、派活供应商／模型／effort 已纳入第一批工作。

## 1. 执行顺序与交付物

先交付默认强度和明确的任务路由，再完成一个项目的真实派活闭环，随后开放跨项目、管理文档和 Git 协作。恢复能力随各步骤实现，最终集中做故障验收。

| 顺序 | 工作包 | 用户可见结果 | 依赖 |
| --- | --- | --- | --- |
| P1 | 默认模型强度 | 设置可保存默认 effort，普通新会话实际使用 | 无 |
| P2 | 派活配置和任务路由 | 派活可指定供应商、模型名、effort，不影响其他会话 | P1 |
| P3 | 后台派活链路 | 创建和启动任务不依赖目标页面已打开 | P2 |
| P4 | 项目主 Agent 与结果闭环 | 项目下有固定主 Agent，能派活并收到可检查结果 | P3 |
| P5 | 跨项目协作 | 一个主 Agent 向多个仓库派活，并集中收到结果 | P4 |
| P6 | 管理文档 | 主 Agent 页面可维护独立管理分支中的文档 | P4；跨项目场景验收依赖 P5 |
| P7 | PR 与上游同步 | 明确 PR 目标，安全同步本地基线，保留任务分支 | P5、P6 |
| P8 | 综合验收与交付 | 重启、失败、迁移、多窗口及支持的远程组合有验证证据 | P1–P7 |

P1 可以独立交付。P1–P4 对应设计方案的单项目阶段，P5、P6、P7 分别对应跨项目、文档和 Git 阶段。本文不把阶段完成等同于全部功能完成。

### 1.2 下一轮的具体执行顺序

按以下顺序接续 P4–P8。每一步都形成可独立验证的提交，代码继续保留在任务分支，开发本功能无需创建 PR。

**第一步：完成依赖任务的后台闭环（P5）**

用“SDK 任务 A 通过检查后，才能启动调用方任务 B”作为验收案例。

1. 扩展现有 `create_task`，增加可选 `depends_on`。返回稳定的任务／会话 ID、有效模型配置和阻塞原因；不新增用户需要操作的工作流层级。
2. `coordination` 拥有依赖关系和检查决定，`agent-control` 拥有持久派发步骤。等待中的任务先保存计划，前置结果通过检查之前不创建代码 worktree、会话进程或发出模型请求。查询和主 Agent 任务页必须能看到该计划。
3. 主 Agent 接受前置结果时触发后台调度；恢复启动也检查待处理计划。按事件触发并合并重复调度，不增加轮询循环。Agent 空闲、进程退出或仅提交结果，都不能放行后续任务。
4. 放行时冻结前置结果版本、项目和提交引用，并作为执行上下文提供。跨仓库依赖只有引用可追溯才算可消费；不自动把 A 的提交合入 B。
5. 拒绝不可访问、缺失、自依赖和成环引用。等待时被取消、前置被删除或当前授权失效，要保留明确阻塞原因；放行后前置产生新结果，不静默更换已冻结的输入。
6. 复用原请求键和资源 ID。等待中切换主会话、接管任务或重启后，按当前负责人及其权限恢复，不能因负责者变化重复建任务。保留原始请求与配置快照供追溯。

主要改动在 `agent-control/api`、`node/mcp-tools.ts`、`node/task-delegation-service.ts`、`node/backend-task-delegation.ts`，以及 `coordination/api/types.ts`、`node/coordinator-service.ts`、主 Agent 任务页和 bootstrap 接线。后台查询需要适配尚未创建运行资源的任务，不能把“查不到 DB 任务行”解释成计划不存在。

完成证据：单元测试覆盖阻塞、错误依赖、并发放行、接管与重启；隔离 Electron 中先确认 B 没有 worktree／进程，A 提交后仍等待，接受 A 后 B 自动创建并启动。重复调用返回相同 ID，实际模型配置与等待前快照一致。

**第二步：补齐结果队列和恢复体验（P4、P5）**

1. 在 ACP 会话队列区分用户消息和后台结果，当前轮次不中断，待处理用户消息优先。协调域保存事件，运行时负责轮次调度，界面展示待处理和失败状态。
2. 为 PTY 及投递状态不明的消息增加可见待处理入口。明确区分已保存、已接收和已消费；无法确认时不自动重放，用户可以查看内容并显式处理。
3. 核对主会话切换、任务接管与结果投递同时发生时，只有当前接收者可以确认和检查。关闭页面、关闭 renderer、应用重启后，结果与检查决定不能丢失。

完成证据：可控 ACP 响应器证明用户消息优先；PTY 场景显示待处理；注入投递确认丢失和进程退出，恢复后没有重复执行，两个窗口同时接受结果只有一个有效决定。

**第三步：交付管理文档（P6）**

1. Git runtime 创建独立历史的管理分支，workspace registry 注册专用 worktree；协调域保存位置和版本引用。代码派活仍从目标项目代码基线创建。
2. 迁移阶段性文档，先复制和校验，再切换引用；迁移中断可重试，原文件保留到迁移确认成功。
3. 主 Agent 文档页复用文件树与编辑器。派活只传相关内容或版本化引用，跨 host 返回可访问的内容，避免依赖桌面绝对路径。
4. 支持本地提交及明确配置后的个人 fork 推送；创建主 Agent 不自动推送。管理分支禁止作为代码 PR 来源。
5. 分别处理空 Git 仓库、非 Git 项目和文档项目失效；协调身份先保留，界面明确哪些操作需要基线或另选文档仓库。

完成证据：编辑、保存、重启恢复和迁移中断通过；管理分支与代码基线没有共同历史；代码任务和代码 PR 的差异没有管理文档；跨仓库主 Agent 的文档只有一个权威存储位置。

**第四步：交付 PR 与上游同步（P7）**

1. 追踪现有 PR 操作链，补齐源任务、推送远端、目标仓库与目标分支的明确表达；复用仓库／PR 域，不另建发布系统。主 Agent 与任务 Agent 均按其权限调用，重复请求识别已有 PR。
2. 同步基于项目配置解析的上游和代码基线。连接恢复、创建代码任务前、已有 PR 合并事件触发检查；同仓库串行并合并重复请求。
3. 只执行可证明安全的本地快进。脏目录、基线分叉、远端改写或 checkout 不可安全更新时报告原因，保留所有任务分支。检查失败保存前后提交，暂停基于该状态自动派活。
4. UI 显示最后检查时间、离线状态和检查输出。个人 fork 远端主分支的推送使用单独明确配置；不随本地同步隐式发生。

完成证据：本地 bare 上游／fork 场景覆盖安全快进和各类拒绝；任务分支提交 ID 不变；PR 契约验证组织仓库目标；测试不向真实组织创建 PR，不触发发布。

**第五步：完成整体验收与交付（P1–P8）**

从干净隔离 profile 真实启动 Electron，把默认模型／effort、跨仓库派活、依赖、接管、结果检查、管理文档和上游同步串成一次验收。再覆盖故障注入、完整退出重启、多窗口与历史记录升级，运行最终本地门禁。

模拟 CLI／ACP、可控上游请求与真实 Agent／远程运行分别记录证据。真实 CLI 或远程环境缺失的组合保留未验证状态并列明条件，不能靠模拟通过宣称这些组合可用。验收使用独立数据库、临时仓库、Agent 配置和 worktree 根目录，不触碰生产配置，不使用 Emdash terminal。

提交说明统一记录用户能完成的操作、测试命令与结果、启动证据和剩余限制。推送、打包、发布按各自明确指令执行。

## 3. P1：设置中的默认模型强度

先形成一个可以独立使用的结果：在设置中选好模型和默认 effort，创建普通会话时实际生效，应用重启后保留。

实施步骤：

1. 扩展 Agent 有效默认配置，保存可选默认 effort；未设置表示跟随模型／适配器默认。具体字段沿用现有设置域，不额外建立全局强度表。
2. 提取共享的启动选择解析函数。输入包含 Agent、host、接入方式、模型选择、显式覆盖和默认配置；输出包含有效值、来源、配置版本和明确错误。
3. 从 Agent 插件和模型能力解析可用强度，兼容已有 Codex 专用配置。具体默认值不兼容时返回错误，不能静默降级。
4. 在设置的 Agent 默认模型旁增加默认强度控件；切换模型时重新校验，支持恢复默认。
5. 普通创建会话、创建任务中的初始会话、主 Agent 和后续 MCP 派活使用同一个解析入口。前端可以预览，后台负责最终校验和冻结有效配置。
6. 在 CLI 和 ACP 边界应用解析结果，保留历史空值行为，不修改已运行会话或已解析的排队任务。

重点检查位置，路径相对 `apps/emdash-desktop/src/core/`：

- `features/agents/api/browser/use-agent-settings.ts` 及对应后端设置接口。
- `features/model-providers/browser/providers-settings-page.tsx`、`api/browser/use-model-source.ts`。
- `features/conversations/api/provider-settings.ts`、`node/provider-settings-service.ts`、创建会话与启动入口。
- `primitives/tasks/api/task-config.ts` 与会话配置 schema。
- Agent 插件的能力和 CLI／ACP 配置适配；通用默认解析不放进供应商专用插件。

完成条件：保存和重启恢复通过；普通会话的有效 effort 与设置一致；明确覆盖优先；缺省值保持历史行为；CLI／ACP 支持路径实际收到值；不支持的组合给出明确错误。

建议提交主题：`feat(agents): add default model effort settings`。

## 4. P2：派活配置与任务级模型路由

统一派活输入：`agent`、`connection`、`supplier_id`、`model`、`effort`。原有省略字段的调用保持可用。

实施步骤：

1. 在 `agent-control/api` 和 MCP schema 中定义输入和有效配置返回值，使用模型供应商的稳定 ID。
2. 复用 P1 解析逻辑，接入优先级：本次显式值、主 Agent 派活默认、设置默认、模型／适配器默认。
3. 模型与网关域增加会话范围的供应商／模型绑定。只传公共别名时保持现有模型目录路径；显式供应商和模型名时使用该绑定。
4. 任务绑定有独立持久引用，不修改公共模型别名；使用现有加密凭据引用和协议校验。未知模型的协议映射必须明确，不能猜测。
5. 将有效配置写入初始会话和派发记录。CLI／ACP 启动、网关请求及用量记录都能追溯到同一任务和选择。
6. 明确路由生命周期：会话暂停或应用重启保留绑定，删除会话后按引用清理；运行中不提前撤销其他会话需要的配置。

重点位置：`agent-control/node/mcp-tools.ts`、`model-providers/api/node/source-launch.ts`、`model-gateway/api/`、`model-gateway/node/` 及实际持有会话路由的服务。必要的网关协议扩展与调用方一起验证，不新增直连供应商捷径。

完成条件：同一供应商的两个模型和两个不同供应商可以分别派活；请求使用正确上游模型及 effort；公共别名、默认配置和其他会话不被覆盖；网关账本仍能归属任务；停用供应商后不会回退到官方登录。

建议提交主题：`feat(model-gateway): support task-scoped model routing`。

## 5. P3：不依赖前台的派活

先把派活变成可验证的后台操作，再接主 Agent UI。

实施步骤：

1. 提供后台派发操作，接收已认证调用者、明确目标项目、任务说明、基线和模型选择；所有输入在后台校验。
2. 按目标项目建立或取得 attachment，调用已有任务与 workspace 创建服务；不用前端 store 判断项目是否可操作。
3. 默认从目标项目代码基线创建。需要从某个任务分支继续时显式指定，管理分支永不成为隐式代码基线。
4. 持久化 `request_id` 和稳定任务、workspace、会话 ID，记录准备、资源创建、会话启动等执行步骤。相同请求重试返回同一结果。
5. 将已有任务创建步骤与会话启动组合起来；会话记录存在不代表进程已启动。启动失败保留资源并可从失败步骤重试。
6. 自动派活操作不再经 renderer dispatcher；需要用户交互的原有操作仍走对应交互路径。

主要复用 `tasks/node/operations/createTask.ts`、会话域启动服务、`workspace-registry` 和 host runtime。新增协调后台 API 使用 typed Wire，通过 manifests 注册。

完成条件：目标项目页面未打开也能创建并启动；相同请求执行两次只有一个任务；在 worktree 建立后注入中断，恢复不会创建第二个分支；模型配置失败不会启动错误会话；无 renderer 时后台行为可测试。

建议提交主题：`feat(agent-control): dispatch tasks through backend services`。

## 6. P4：项目主 Agent 与结果闭环

这是第一批完整产品体验的交付点。

实施步骤：

1. 建立协调者记录、项目默认绑定、任务负责关系、派发记录和结果事件。为项目默认绑定及幂等请求加唯一约束；迁移与恢复都能重复执行。
2. 协调者绑定显式角色的运行容器，复用会话和 workspace。更新任务类型消费者，排除普通任务统计和常规归档动作，避免通过任务名称识别角色。
3. 项目创建事件幂等建立主 Agent；升级时补齐记录，资源按需准备，不自动为所有项目启动模型进程。
4. 在项目下面增加固定主 Agent 行，注册主 Agent 页面及导航。普通任务、置顶、项目排序和分组行为保留。
5. 提供任务说明和任务引用列表，支持主 Agent 派活；普通任务的说明只有一个权威来源。
6. 增加提交结果能力，保存分支／提交、摘要、验证证据和未解决项。结果进入待检查，进程空闲或退出不自动置为完成。
7. 通过持久事件队列唤起或通知主 Agent，忙时排队，按事件 ID 去重。无法确认投递的 PTY 路径保留待处理，不强行向活跃输入注入消息。

这一工作包引入 `features/coordination/` slice。数据库通过项目规定的生成流程修改，主 Agent UI 通过 contributions 注册。文档页在 P6 前保持未开放，不能显示已完成的管理分支能力。

## 7. P5：跨项目协作

实施步骤：

1. 扩展项目发现和任务查询，区分调用来源、目标项目、关联项目与操作授权。使用稳定 ID，不接受任意路径代替项目身份。

3. 子任务继承明确的可用权限，不能扩大调用者权限；不同 host 的路径、凭据和运行时由目标项目决定。
4. 增加按需显示的跨项目主 Agent 入口及关联项目设置。项目主 Agent 也可以跨项目派活，入口不被迫迁移。
5. 实现一个任务一个负责者、显式接管、简单依赖和阻塞原因。前置任务通过检查后再启动依赖任务。

完成条件：一个主 Agent 在两个临时仓库中派出两个任务，任务分别留在各自项目，结果回到同一主 Agent；移动项目分组不改变授权；无权目标报错且不在来源项目误建任务；两个主 Agent 不能同时取得同一任务的控制权。

### P5 补充：任务原子接管

MCP 的 `take_over_task` 和主 Agent 任务页支持显式接管。先读取当前负责人，再携带预期负责人 ID（无负责人时为 null）操作；负责人已变化则拒绝。接管仅允许可访问的普通代码任务，主 Agent 容器与自动化运行不能接管。成功请求重复执行不会产生第二条接管记录。

负责人记录、结果及事件在同一个 SQLite 事务中转移，保留原任务 ID、项目、分支、会话和结果版本。未确认通知转给新负责人，已确认结果保留已读状态。worker 的项目授权只保留新负责人可授予的部分；旧负责人不能再控制该任务或检查其结果。并发接管只有一个目标能成功；写入失败不会出现两个负责人或任务丢失。

协调记录升级为版本 3，并保存接管历史。版本 1／2 可升级；读到不认识的本人或目标任务授权记录时拒绝操作，不将其当作普通无范围调用者。后台派发在注册任务关系时再次检查目标项目及 worker 授权，避免准备期间负责人或权限变化后继续越权创建。

隔离 SQLite 故障测试通过触发器使第二个负责人写入失败，确认原负责人、结果和事件全部保留；去掉故障后重试并重建服务，只有新负责人持有任务与结果。12 个协调／控制测试文件、96 项测试通过，包含注册阶段权限变化的专项检查。
